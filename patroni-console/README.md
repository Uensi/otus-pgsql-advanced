# Patroni Console (ядро)

Мониторинг и управление кластером Patroni 4 + etcd 3.6. Этапы 1–3: статус, операции, события и уведомления.

Что уже есть:
- статус кластера: лидер, роли, состояние, таймлайн, лаг, LSN, теги, pending restart, пауза;
- предупреждения: нет лидера, несколько лидеров, нода недоступна или не в DCS, лаг выше порога или неизвестен,
  расхождение таймлайнов, нет кандидата для failover, запланированный switchover;
- etcd (только чтение): статус каждого endpoint, лидер raft, размер базы, alarms, кворум;
- история переключений (`/history`) и глобальный конфиг (`GET /config`);
- вход с серверными сессиями, роли `viewer` / `operator` / `admin`, CSRF, ограничение попыток входа, аудит в SQLite.

- операции (этап 2), описаны ниже.

- события и уведомления (этап 3), описаны ниже.

Чего пока нет (следующий этап): редактор глобального конфига через `PATCH /config` с историей и откатом.

## Операции

| Операция | Роль | Что делает |
|---|---|---|
| switchover | operator | смена лидера сейчас или по расписанию (`scheduled_at` с часовым поясом) |
| отмена запланированного switchover | operator | `DELETE /switchover` |
| пауза / снятие паузы | operator | `PATCH /config {"pause": true / null}` |
| рестарт ноды | operator (лидер — admin с force) | `POST /restart`, ждёт возврата ноды в норму |
| rolling restart | operator | реплики по одной, затем switchover на лучшего кандидата, затем бывший лидер; стоп на первой ошибке |
| failover | admin | `POST /failover` на кандидата; при живом лидере только с force |
| reinit реплики | admin | `POST /reinitialize`, ждёт возврата реплики |

Правила безопасности:
- перед запуском — проверки по свежему снимку кластера и `/config`: уровни «нельзя», «опасно» (только admin с force),
  «внимание» (нужно подтвердить). Проверяются лаг кандидата против `maximum_lag_on_failover`, тег `nofailover`,
  `synchronous_mode`, таймлайн, доступность, пауза, уже запланированный switchover и т.д.;
- пользователь вводит имя кластера;
- изменяющий запрос в Patroni отправляется ровно один раз и не повторяется. Если ответ потерян (таймаут чтения),
  результат определяется по состоянию кластера;
- успех считается по кластеру, а не по ответу: лидер сменился, старый лидер вернулся репликой (иначе статус «с замечаниями»);
- одна активная операция на кластер (уникальный индекс в SQLite), `Idempotency-Key` защищает от двойного нажатия;
- каждая операция и её итог пишутся в аудит; ход виден в таблице операций. После перезапуска консоли
  незавершённые операции помечаются «прервана».

## События и уведомления

Фоновый наблюдатель раз в `watch.interval` секунд проверяет каждый кластер и etcd и ведёт ленту событий
(раздел «События» на странице, `GET /api/clusters/<кластер>/events`).

- Проблема (нет лидера, нода недоступна, лаг выше порога, реплика не в streaming, расхождение таймлайнов,
  пауза, нет кворума etcd, alarm etcd, endpoint etcd недоступен и т.д.) открывается, только если продержалась
  `watch.confirm` проверок подряд, и закрывается так же. Короткий дребезг уведомлений не вызывает.
- Смена лидера записывается всегда. Во время операции из консоли или по запланированному switchover это `info`,
  иначе `critical` «незапланированная смена лидера».
- Открытые проблемы и последний лидер хранятся в SQLite: после перезапуска консоли повторных уведомлений нет.
- Уведомления уходят в webhook (JSON с `event_id`, `level`, `code`, `node`, `text`, `message`) и Telegram.
  Каждый канал получает события от своего `min_level`. Событие и очередь уведомлений пишутся одной транзакцией,
  при ошибке отправка повторяется с нарастающей паузой (до 6 попыток). Повторная доставка возможна,
  поэтому получателю webhook стоит отбрасывать дубли по `event_id`.
- Кнопка «Отправить тестовое уведомление» (admin) проверяет все каналы.

## Запуск

```bash
pip install -r requirements.txt
cp config.example.yaml /etc/patroni-console/config.yaml   # заполнить ноды, etcd, пользователей
python -m patroni_console.hashpw                           # хеш пароля для users[].password_hash
export PATRONI_CONSOLE_SECRET=$(python3 -c 'import secrets; print(secrets.token_urlsafe(48))')
export PATRONI_REST_PASSWORD=...  ETCD_PASSWORD=...
PATRONI_CONSOLE_CONFIG=/etc/patroni-console/config.yaml \
  gunicorn -w 1 --threads 8 -b 127.0.0.1:8080 'patroni_console.wsgi:app'
```

Строго один процесс (`-w 1`): наблюдатель и отправщик уведомлений работают внутри него, второй воркер
продублирует уведомления. Снаружи — через HTTPS-прокси (nginx).

## Тесты

```bash
python -m pytest -q
```

Тесты не ходят в сеть: Patroni и etcd подменяются заготовками ответов (`tests/fakes.py`),
операции проверяются на имитаторе кластера (`tests/sim.py`).

## Устройство

```
patroni_console/
  config.py   загрузка и проверка конфига (секреты только через ${ENV}, пароли только хешами)
  patroni.py  клиент REST API Patroni (ошибки не маскируются)
  etcd.py     read-only диагностика etcd v3
  status.py   снимок состояния кластера и предупреждения (build() — чистая функция)
  store.py    SQLite: сессии, аудит, попытки входа, операции
  ops.py      проверки перед операциями и выполнение с контролем результата
  watcher.py  наблюдатель: условия, события, смена лидера
  notify.py   отправка уведомлений из очереди (webhook, Telegram)
  web.py      HTTP API; каждый маршрут объявляет минимальную роль, без объявления — отказ
  static/     страница статуса (без внешних библиотек и CDN)
```
