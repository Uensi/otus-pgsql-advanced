# Регламент DBA: работа с кластером через Patroni Console

## Ежедневный осмотр (2 минуты)

1. **Баннер** вверху страницы. Зелёный — норма. Оранжевый — есть замечания, красный — авария.
2. **Обзор → Репликация.** Корона отмечает лидера. Полоса показывает лаг реплики. Оранжевая полоса — лаг выше
   `max_lag_bytes` кластера, красная — реплика не в streaming или лаг неизвестен.
3. **Обзор → Ноды.** Метка «нужен рестарт» — изменён параметр, который применяется только после рестарта.
4. **Обзор → etcd.** Должен быть кворум и один лидер raft. Alarm `NOSPACE` — etcd перестал принимать запись,
   Patroni скоро потеряет лидера (нужны `etcdctl defrag` и `etcdctl alarm disarm` на стороне etcd).
5. **События.** Цифра на вкладке — сколько проблем открыто сейчас.

## Что означают уведомления и что делать

| Уведомление | Уровень | Действие |
|---|---|---|
| нет лидера | critical | Проверить etcd (кворум), логи Patroni на нодах. Если кворума нет — восстанавливать etcd, Patroni сам выберет лидера. Если лидера нет при живом etcd дольше `ttl` — Failover на самую свежую реплику. |
| незапланированная смена лидера | critical | Patroni сделал failover. Выяснить причину по логам старого лидера. Проверить, что старый лидер вернулся репликой (событие «устранено» по недоступности). Если не вернулся — Reinit. |
| нода недоступна | warning (critical для лидера) | Проверить сервис patroni и сеть до порта 8008. |
| лаг выше порога | warning | Нагрузка на запись, сеть, I/O реплики, долгие запросы на реплике (`hot_standby_feedback`). Такая реплика не будет кандидатом в failover. |
| реплика не в streaming | warning | Смотреть лог PostgreSQL реплики. Если WAL уже удалён на лидере — Reinit. |
| расхождение таймлайнов | warning | Реплика не перешла на новый таймлайн после переключения. Обычно помогает рестарт, иначе Reinit. |
| нет кандидата для failover | warning | Все реплики отстают, недоступны или помечены `nofailover`. Автоматический failover не сработает. |
| кластер на паузе | warning | Автоматический failover выключен. Снять паузу после работ. |
| etcd: нет кворума / alarm | critical | Работа с etcd. Patroni при потере DCS переводит лидера в read-only (если не включён `failsafe_mode`). |
| глобальный конфиг изменён вне консоли | warning | Кто-то сделал `patronictl edit-config` или PATCH /config. Разница видна во вкладке «Конфиг → История», там же откат. |

## Плановые работы

### Switchover (смена лидера)
**Операции → Switchover.** Выберите кандидата или оставьте выбор Patroni. Консоль заблокирует кандидата,
если у него лаг больше `maximum_lag_on_failover`, тег `nofailover`, другой таймлайн, он недоступен или
не синхронный при `synchronous_mode`. Можно запланировать на время (с часовым поясом браузера).
Успех: сменился лидер и старый вернулся репликой. Если старый не вернулся — статус «с замечаниями».

### Обновление PostgreSQL minor / ОС на нодах
1. **Пауза не нужна.** Работайте по одной реплике: остановили patroni → обновили → запустили →
   дождались зелёного статуса ноды.
2. Последним — бывший лидер: сначала **Switchover** на обновлённую реплику, затем работы на старом лидере.

### Изменение параметров PostgreSQL
**Конфиг → Изменения**, например `postgresql.parameters.work_mem = 64MB`. Консоль покажет разницу и проверки:
- параметр, требующий рестарта, — предупреждение; после применения выполните **Rolling restart**
  («только ноды, которые ждут рестарта»): сначала реплики, затем switchover и бывший лидер;
- уменьшение `max_connections`, `max_worker_processes`, `max_wal_senders`, `max_prepared_transactions`,
  `max_locks_per_transaction` — предупреждение: на репликах эти значения не могут быть меньше, чем на лидере;
- `listen_addresses`, `port`, `hot_standby` и т.п. задаются в patroni.yml ноды — консоль такие изменения не примет;
- `loop_wait + 2 × retry_timeout` должно быть не больше `ttl`.

Каждое изменение сохраняется в истории (до/после, кто, когда). **Откатить это изменение** вернёт ключи,
которые оно затронуло, к прежним значениям.

### Пауза
Нужна, когда вы сами останавливаете PostgreSQL на лидере и не хотите, чтобы Patroni сделал failover.
Не забудьте **Снять паузу** — консоль напоминает об этом предупреждением, пока пауза включена.

## Аварийные действия

### Failover (только admin)
Используйте, когда лидера нет и Patroni сам не выбирает нового (например, все реплики отстают больше
`maximum_lag_on_failover`). Консоль предупредит о возможной потере данных и покажет лаг кандидата.
Failover при живом лидере требует флажка «принудительно».

### Reinit реплики (только admin)
Удаляет данные реплики и копирует их заново с лидера (`pg_basebackup`). Применяйте, когда реплика
не может догнать лидера или разошлась по таймлайну. Лидера переинициализировать нельзя.

## Правила, которые консоль соблюдает сама

- Перед каждой операцией — свежие проверки; «Нельзя» блокирует, «Опасно» — только admin с флажком,
  «Внимание» — нужно подтвердить. Всегда нужно ввести имя кластера.
- Изменяющий запрос в Patroni отправляется один раз. Если ответ потерян, консоль не повторяет запрос,
  а определяет результат по состоянию кластера.
- На кластере одновременно выполняется не больше одной операции.
- Всё пишется в аудит (вкладка не нужна: `GET /api/audit`, роль admin).
