# Patroni Console

Веб-консоль управления и мониторинга PostgreSQL/Patroni: кластеры, метрики, ERD-схема,
анализатор запросов (EXPLAIN + рекомендации индексов), блокировки, DBA-инструменты,
SQL-консоль, операции (switchover/failover/restart), бэкапы wal-g через агент, слоты
репликации, отчёты (аналог PWR), алерты, RBAC и аудит. Мультикластер (Центр).

Платформа жизненного цикла PostgreSQL: реестр хостов + ОС-метрики + прогноз диска,
логические дампы (pg_dump) и физические (wal-g), NFS, уведомления по e-mail/Telegram,
обслуживание (pg_repack + планировщик), шаблоны конфигов, здоровье DCS (etcd/Consul),
AI-ассистент, экспорт в Prometheus/Zabbix.

Скриншоты всех экранов: [docs/screenshots](docs/screenshots/index.html) (48 шт., демо-режим).

## Возможности

### Кластер и инфраструктура
- **Кластер** — живой статус узлов (роль, LSN, лаг), график лага реплик.
- **Центр** — сводка по всем кластерам из `config.yaml` + переключение активного.
- **Хосты** — реестр: агенты (load, CPU, RAM, диски, ядро, службы, версия PG) + прогноз
  заполнения диска (линейный по истории), kernel-предупреждения (swappiness/overcommit/THP),
  standalone-инстансы без Patroni (пробинг, версия, размер БД), управление службами
  (postgresql/patroni/etcd/consul/msmtp — белый список).
- **DCS** — здоровье etcd/Consul (члены, лидер), `synchronous_standby_names` + sync_state
  реплик с лидера; авто-обнаружение адресов DCS из `patroni.yml` через агентов (admin).

### Метрики и мониторинг
- **Метрики** — TPS, cache hit, соединения, tuples/s, блокировки, deadlocks, temp files,
  размер БД, лаг репликации (сбор агентом каждые ~15 с), ОС-метрики хостов.
- **Отчёты (PWR)** — снимки каждые 60 с, TPS/cache/growth/top-запросы за период.
- **Алерты** — редактируемые правила по метрикам (порог/оператор/важность, вкл/выкл,
  удаление), история firing/resolved, индикатор в шапке.
- **Уведомления** — маршрутизация по важности (critical/warning/info) через e-mail
  (msmtp или SMTP) и/или Telegram; авто-отправка при срабатывании/восстановлении алерта;
  тестовая отправка; журнал.
- **Экспорт** — `GET /metrics` (Prometheus text: агенты, TPS, cache, лаг, ОС-метрики)
  и `GET /api/metrics/export?format=zabbix|json` (для `zabbix_sender -i`).

### Бэкапы и восстановление
- **Бэкапы** — полный/дельта wal-g, ротация, верификация, restore/PITR в отдельный
  каталог, расписание (физическое), клонирование (`clone_restore`: каталог + конфиг
  порт +100 + старт-скрипт, без автозапуска), инспекция клона (`clone_inspect`:
  версия, pg_controldata, размер, recovery-сигнал).
- **Логические дампы** — pg_dump (custom/dir/sql-zstd, потоки `-j`, сжатие), список,
  ротация по TTL, удаление; NFS-монтирование (белый список точек), отчёты по e-mail
  через агента (msmtp); расписание дампов (`dump_schedule.json`).

### Обслуживание и конфигурация
- **Обслуживание** — дефрагментация: pg_repack (онлайн) или VACUUM FULL через агента
  (метод auto/repack/vacuum); планировщик maintenance в окно (дни недели + время),
  сам находит самые раздутые таблицы по `min_bloat_pct`.
- **Шаблоны конфигов** — пресеты «1С высокая производительность / 1С Postgres Pro /
  1С после аудита / OLTP / OLAP / консервативный»; сравнение «сейчас → после», применение
  через Patroni `/config` (с подтверждением, admin), история применений.
- **Оптимизация кластера** — каталог параметров PostgreSQL/Postgres Pro с пояснениями и
  системно-зависимыми рекомендациями (RAM/CPU/соединения + тип диска SSD/NVMe/RAID):
  shared_buffers, autovacuum, планировщик, параллелизм, I/O, специфика 1С (online_analyze,
  plantuner, JIT, merge join, GEQO).

### Риски потери данных и простоя (экран «Риски»)
- **Wraparound XID / MultiXact** — возраст `datfrozenxid` по базам в % от предела 2^31,
  оценка «дней до остановки записи» по реальному расходу XID, таблицы, которые держат
  возраст, и запуск `VACUUM (FREEZE)` в фоне.
- **RPO** — возраст последнего бэкапа и последнего полного, `pg_stat_archiver` (архивация
  падает / выключена / очередь `.ready`), история **автоматических проверок
  восстановления**: агент разворачивает последний бэкап во временный каталог, применяет
  WAL, поднимает PostgreSQL на отдельном порту, проверяет чтение баз и удаляет копию.
- **Слоты репликации** — `wal_status` (lost/unreserved/extended), объём удерживаемого WAL,
  неактивные слоты без `max_slot_wal_keep_size`.
- **Лаг во времени** — write/flush/replay lag в секундах из `pg_stat_replication`.
- Всё это попадает в сводку здоровья кластера и в правила алертов (`xid_age_pct`,
  `backup_age_h`, `archive_failing`, `slots_at_risk`, `replay_lag_s`).

### Производительность
- **Активные сессии (ASH)** — раз в секунду снимок активных сессий на каждом узле;
  график средней нагрузки по классам ожиданий (CPU, IO, Lock, LWLock, Client…),
  топ ожиданий, запросов, пользователей и баз за период. Ответ на «что тормозило в 14:30».
- **Запросы и регрессии** — история `pg_stat_statements` (снимок раз в 10 минут, неделя):
  топ за период и запросы, у которых среднее время выросло в 2+ раза.
- **Контрольные точки и WAL** — доля вынужденных КТ, запись бэкендами, `wal_buffers_full`,
  доля FPI — с конкретными рекомендациями по `max_wal_size`, bgwriter, `wal_compression`.
- **Долгие операции** — прогресс VACUUM, ANALYZE, CREATE INDEX, CLUSTER, basebackup, COPY
  на всех узлах с оценкой оставшегося времени.
- **Аудит индексов** (DBA → «Аудит индексов») — невалидные, дубли, перекрытые, FK без
  индекса, неиспользуемые; готовый SQL исправления с `CONCURRENTLY`.

### Эксплуатация и безопасность
- **Журналы PostgreSQL** — агент читает хвост текущего лога, консоль группирует ошибки,
  deadlock'и, медленные запросы, временные файлы, ожидания блокировок, автовакуум и
  неудачные входы; проверка настроек логирования.
- **Аудит безопасности** — суперпользователи, MD5 вместо SCRAM, `trust` по сети в
  `pg_hba.conf`, SSL и незашифрованные подключения, CREATE в `public`, журналирование
  входов; оценка 0–100 и SQL исправления.
- **Обновления** — отставание от последней минорной версии, конец поддержки (EOL),
  проверки перед `pg_upgrade` (2PC, логические слоты, reg*-типы, расширения, локали,
  checksums) и пошаговый план для кластера Patroni. Справочник версий —
  `pg_versions.json`, обновление: `python3 tools/update_pg_versions.py`.
- **Вход через LDAP / Active Directory** с сопоставлением групп ролям (вложенные группы AD).
- **Еженедельный отчёт** — страница для печати/PDF (риски, бэкапы, алерты, рост баз и
  прогноз на 30 дней, диски, тяжёлые запросы, безопасность, версии) и рассылка по расписанию.

### SQL и данные
- **Схема / ERD** — диаграмма схемы с колонками/ключами, экспорт PNG.
- **Анализатор** — медленные/текущие запросы (pg_stat_statements) и свой запрос:
  дерево EXPLAIN, проблемы плана, рекомендации индексов, переписывание.
- **Блокировки / DBA** — locks, deadlocks, bloat, vacuum, неиспользуемые индексы,
  соединения, тюнинг параметров, delayed replica, kill/cancel.
- **SQL-консоль** — выполнение SELECT/DML/DDL на выбранной ноде (опасные команды заблокированы).

### AI-ассистент
- **🤖 AI** — локальный ассистент DBA (без внешних API, работает в закрытой сети):
  ответы по темам с учётом живого состояния (лаг, bloat, idle-in-tx, конфиг, бэкапы,
  Patroni, вакуум); объяснение EXPLAIN-планов; тюнинг-советы по текущему `/config`
  Patroni; кнопка «объяснить план» в Анализаторе запросов; 🩺 диагностика — сводка
  проблем по живому снимку (алерты, офлайн-агенты, лаг, диски с прогнозом, ядро);
  история диалога (`assistant_log.jsonl`).

### Администрирование
- **Админ** — расширения, роли, табличные пространства, diff pg_settings и patroni.yml.
- **Аудит** — журнал действий пользователей (только admin).

## Быстрый старт

### Демо без кластеров (5 минут)

Показать консоль коллегам или клиенту, не имея доступа к Patroni:

```bash
pip install -r requirements.txt
PATRONI_CONSOLE_DEMO=1 PATRONI_WEB_CONFIG=config.demo.yaml PATRONI_CONSOLE_DATA=.demo-data python app.py
```

Откройте http://127.0.0.1:5000, вход **demo / demo**. Данные сгенерированы и меняются
во времени (лаг, TPS, диски); любые действия (switchover, бэкап, VACUUM) в демо ничего
не выполняют. Через Docker: `CONSOLE_CONFIG=config.demo.yaml PATRONI_CONSOLE_DEMO=1 docker compose up`.

### Рабочая установка

Требуется Python 3.10+ и сетевой доступ с сервера консоли к REST API Patroni (:8008)
и к PostgreSQL (:5432) на узлах.

```bash
cp config.example.yaml config.yaml && chmod 600 config.yaml   # заполнить узлы, пароли, secret
pip install -r requirements.txt
python app.py                                                 # dev-сервер на 0.0.0.0:5000
```

## Продакшен

**Docker** (рекомендуется):

```bash
docker compose up -d          # config.yaml монтируется только для чтения, данные — в томе console-data
```

**systemd + gunicorn**: см. `deploy/patroni-console.service` (инструкция в шапке файла),
HTTPS через nginx — `deploy/nginx.conf.example`.

> Консоль запускается **строго одним процессом** (`workers = 1`, параллелизм — потоками,
> см. `deploy/gunicorn.conf.py`). Реестр агентов, история метрик и планировщики бэкапов
> живут в памяти: при нескольких воркерах агенты «пропадают», а задания по расписанию
> выполняются несколько раз.

Проверки для балансировщика/мониторинга: `GET /healthz` (процесс жив) и
`GET /readyz` (отвечает хотя бы один узел Patroni; иначе 503). Обе — без авторизации.

Каталог данных (аудит, история алертов, расписания, настройки уведомлений):
переменная `PATRONI_CONSOLE_DATA` (в Docker — `/app/data`). Без неё — рядом с кодом, как раньше.

### Безопасность

- Пароли пользователей в `config.yaml` можно хранить хешами werkzeug (`scrypt:`/`pbkdf2:`).
- Сессии: HttpOnly, SameSite=Lax, 12 ч; при `cookie_secure: true` — только HTTPS (+HSTS).
- Защита от CSRF: межсайтовые изменяющие запросы отклоняются по `Sec-Fetch-Site`/`Origin`.
- Заголовки: CSP без внешних источников, `X-Frame-Options: DENY`, `nosniff`.
- Ограничение перебора паролей: 10 неудачных входов с IP за 15 минут.
- `/api/agent/*` без сессии принимает только регистрацию/опрос/результат агентов (по ключу).
- `/metrics` можно закрыть токеном `web.metrics_token`.
- Опасные операции (failover, reinit, перезапуск кластера) требуют ввести имя узла/кластера.

## Интерфейс

- **Обновление без мерцания.** Экраны опрашивают сервер раз в 3–60 с, но DOM не
  перерисовывается целиком: `static/ui-kit.js` сравнивает старую и новую разметку и меняет
  только изменившиеся узлы (morph). Сохраняются фокус, выбор в списках, прокрутка,
  выделение текста; графики обновляют точки в тех же наборах данных.
- **Сводка здоровья** на экране «Кластер»: одной фразой — исправен / требует внимания /
  авария, и список причин (нет лидера, реплика отстаёт, узел ждёт рестарта, пауза, агент
  офлайн). Учитывает состояние `streaming` реплик Patroni 3.x.
- **Подсказки DBA**: наведите курсор на заголовок колонки или метрику (TL, LSN, лаг,
  bloat, idle in transaction…) — короткое объяснение, что это и какие значения нормальны.
- Экран хранится в адресе (`#hosts`, `#backups`…): ссылку можно отправить коллеге.
- Светлая/тёмная тема (по умолчанию — как в системе), адаптивная вёрстка.

## Конфигурация `config.yaml`

`config.yaml` **не изменяется** платформенными функциями — все новые настройки живут
в sidecar-файлах JSON рядом с ним:

- `web`: host, port, `secret` (обязателен в проде), `cookie_secure` (если HTTPS).
- `postgres`: параметры подключения (user/password/database/port) к кластерам.
- `agents.key`: общий ключ агентов (обязателен, иначе агенты не зарегистрируются).
- `clusters`: список кластеров; у каждого `name` и `nodes` (Patroni REST :8008).
- `users`: логин/пароль/роль (viewer|dba|admin).
- `patroni.config_path`: путь к patroni.yml на нодах (для агентских операций).

Sidecar-файлы (создаются при первом сохранении через UI/API):
`backup_schedule.json` (расписание wal-g), `dump_schedule.json` (расписание pg_dump),
`maint_schedule.json` (расписание обслуживания), `config_history.jsonl` (история
применения шаблонов), `notify_config.json` + `notify_log.jsonl` (уведомления),
`dcs_config.json` (адреса etcd/Consul), `alerts_rules.json` + `alerts_history.jsonl`,
`assistant_log.jsonl` (история AI-диалога).

## Агент на нодах

```bash
sudo PATRONI_CONSOLE_URL=http://<console>:5000 PATRONI_CONSOLE_KEY=<ключ> \
     PG_PASSWORD=<пароль суперпользователя> python3 agent.py
```

Агент регистрируется, отдаёт метрики (в т.ч. ОС-метрики) и исполняет команды:
бэкапы wal-g (full/delta/restore/PITR/clone), pg_dump (create/list/rotate/delete), NFS,
чтение patroni.yml, обнаружение DCS, управление службами (белый список), msmtp-отчёты,
pg_repack/VACUUM FULL, чтение журнала PostgreSQL, проверка восстановления из бэкапа.
Требует root (права на wal-g и правку patroni.yml).

Необязательные переменные окружения агента:

| Переменная | Назначение |
|---|---|
| `PATRONI_AGENT_PATRONI_YML` | путь к patroni.yml (если на хосте несколько экземпляров или путь нестандартный) |
| `PATRONI_AGENT_WALG_CONFIG` | конфиг wal-g (по умолчанию `/var/lib/pgsql/.walg.json`, `/etc/walg.json`) |
| `PATRONI_AGENT_RESTORE_BASE` | каталог для restore/PITR/клонов и проверок восстановления (`/var/lib/pgsql/restore`) |
| `PATRONI_AGENT_DUMP_BASE` | каталог логических дампов (`/var/lib/pgsql/dumps`) |
| `PATRONI_AGENT_PG_HOST` | адрес PostgreSQL для агента (по умолчанию — из `postgresql.listen`) |
| `PATRONI_AGENT_NONROOT=1` | запуск без root (контейнер, стенд): wal-g и pg_ctl от текущего пользователя |

Для дельта-бэкапов в конфиге wal-g нужен `WALG_DELTA_MAX_STEPS` > 0. Восстановленные
каталоги (restore, PITR, клон) создаются с `archive_mode = off`: запущенная копия не
пишет WAL в хранилище боевого кластера.

## Тесты

```bash
python -m unittest discover -s tests -p 'test_*.py'
```

Модульные тесты запускаются без живой БД (psycopg2 замокан): маршруты, авторизация, RBAC,
CSRF, валидация ввода, разбор журналов, демо-данные. Данные пишутся во временный каталог.

### Сквозной тест на живом кластере (E2E)

`tests/e2e/stand.sh` поднимает без root и Docker: etcd, два узла Patroni (PostgreSQL),
wal-g с файловым хранилищем, два агента и консоль. `tests/e2e/e2e_test.py` проверяет
весь путь «консоль → агент → wal-g → PostgreSQL»: полный и дельта-бэкап, **PITR на момент
времени с проверкой данных до/после точки**, обычное восстановление, автоматическую
проверку восстановления, клон, pg_dump, switchover туда и обратно, а также все DBA-экраны.

```bash
# каталог с wal-g (wal-g-pg-*-amd64.tar.gz → walg.tar.gz), etcd (etcd.tar.gz) и python-колёсами (wheels/)
PCTEST_DL=~/pctest-dl PCTEST_SRC=$PWD bash tests/e2e/stand.sh install
PCTEST_SRC=$PWD bash tests/e2e/stand.sh up
PYTHONPATH=~/pctest/pylibs python3 tests/e2e/e2e_test.py
bash tests/e2e/stand.sh clean
```
